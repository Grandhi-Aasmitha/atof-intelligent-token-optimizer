# Phase 6 — VS Code integration

One extension, one local service, one dashboard. The extension shows the shared local optimization switch in the status bar, opens the existing Control Center and exposes an optional owned model request. The existing native Copilot, Codex IDE and Claude sessions remain unchanged unless configured with an approved integration.

~~~mermaid
flowchart TD
 A[VS Code user invokes ATOF Ask AI] --> B[Task plus explicitly selected text]
 B --> C[Loopback preparation adapter]
 C --> D[Shared ON/OFF and dynamic engine]
 D --> E[Single prepared input or original fallback]
 E --> F[User-approved VS Code model API]
 F --> G[AI response in untitled editor]
 C --> H[Single dashboard: preparation estimates]
 M[Optional configured Copilot MCP] --> D
~~~

## Supported paths
VS Code Language Model API: https://code.visualstudio.com/api/extension-guides/ai/language-model
Extension MCP provider: https://code.visualstudio.com/api/extension-guides/ai/mcp
Agent hooks: https://code.visualstudio.com/docs/agent-customization/hooks

The documented model API lets extensions own their own model input. ATOF asks for consent, selects an available Copilot vendor model, prepares task and selection locally, and invokes sendRequest once with a single message. No arbitrary provider credentials, no extra original context, no model-call retry. It does not attach the editor's whole file or conversation history. Classification is conservative: recognizable diff/test/error evidence uses the relevant structured slot; other selections use generic context. Source slicing and repository retrieval are not automatically applied to incomplete selections. The user can cancel. If preparation fails, explicit confirmation is needed before sending the original. The dashboard records preparation, not provider consumption or billing; a successful response is shown in the editor. No model traffic is generated by status polling.

The optional MCP definition is disabled until the user chooses an approved Python executable, stored in extension-local global state. It uses the same installed ATOF package and shared local policy, not a separate engine or dashboard. Do not register if the previous workspace MCP configuration already provides ATOF. Remove the extension-provided definition independently. Codex IDE and Claude use their approved MCP configuration, where supported. No Codex CLI or automatic native interception. Hook context additions are not proof of replacement. Remote workspaces and browser extension are later work.

## Build and install
~~~powershell
git pull --ff-only origin feature/phase-1-foundation
py -3.11 scripts/start_atof.py --port 8081
~~~
In another terminal:
~~~powershell
cd ide/vscode
npm run check
npm test
npm run package
~~~
Requires Node and approved installed VSCE (npm run package uses vsce, no automatic install). Install the resulting VSIX from VS Code Extensions > Install from VSIX. Existing extension ID retained for upgrade. Default backend port 8081; override atof.apiUrl for an approved local origin. The extension does not install or start the backend automatically in this phase. Single installer remains Phase 12.

## Acceptance
Backend: tests/test_vscode_phase6.py verifies owned adapter and global switch, preserving preferences, native denial and unverified status. Node tests cover selection classification, prompt preservation, ON/OFF response validation, single model invocation/no retry and loopback origin. Use --verify for Python regressions. A local smoke or mock model is not a real VS Code acceptance test. With approved VS Code and model, select synthetic repeated error text, invoke ATOF: Ask AI with ATOF, select the model, and check the response and matching preparation record. Toggle OFF and repeat; original evidence must be retained. Compare full prepared-input estimates and model quality separately; provider savings remain unverified. Verify optional MCP discovery and explicit invocation separately. Native normal-chat automatic replacement remains open.
